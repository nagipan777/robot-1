# Create3前後振動の診断結果

採取日: 2026-10-13
入力: 既知目標 `odom (0.0, 0.25)`
安全設定: `max_linear_speed=0.08 m/s`、Create3 reflex有効

## 結論

観測した後退指令は`vision_turn_controller`由来ではなく、`motion_control`のBUMP反射が生成した`-0.14 m/s`である。8回の後退開始すべてについて、4〜94 ms前に`bump_right`が記録された。上流の`/cmd_vel_unstamped`とリレー後の`/cmd_vel`には負のlinear.xが一度もない。

## ROSグラフ

- `/cmd_vel_unstamped`: Publisherは`vision_turn_controller`のみ。`motion_control`と`unstamped_cmd_relay`が両方購読。
- `/cmd_vel`: `unstamped_cmd_relay`が配信し、`motion_control`が購読。
- `/diffdrive_controller/cmd_vel`: `motion_control`が配信し、Gazebo bridgeが購読。
- よって同じNavigation指令がUnstamped経路とStamped経路の二経路で`motion_control`へ入る。
- 診断時の`/cmd_vel`には`cmd_vel_bridge`もPublisherとして表示されるが、記録値はリレー値と一致し、負速度はない。

## 時刻・遅延

- Navigationの鮮度判定は`time.monotonic()`で統一されている。
- `motion_control`はシミュレーションROS時刻で受信時刻を保存し、0.5秒の停止判定をする。
- `unstamped_cmd_relay`は`use_sim_time`未設定のため、`/cmd_vel` headerはシステムROS時刻。
- `motion_control`出力、odom、hazardのheaderはシミュレーション時刻。この時計領域の混在は存在する。
- ただし`motion_control`は受信したheaderをタイムアウト計算に使わず、callback時の`this->now()`を使うため、今回の負速度生成とは一致しない。
- Unstamped配信間隔は中央値0.100 s、99 percentile 0.193 s。リレー遅延は中央値3.5 ms、99 percentile 90.8 ms。
- 約1秒の最大入力間隔は観測されたが、負速度開始はすべてBUMP直後であり、タイムアウトはゼロ停止しか生成できない。

## 原因候補の優先順位

1. **BUMP安全反射（確定度: 高）**: 全8回でBUMP→`-0.14`→odom負速度の順序が一致。
2. **開始位置付近のドックまたは衝突形状（高）**: hazardが常に`bump_right`。目標が左方向でも周期的に右バンパーが接触しているため、VNC表示だけでなくGazebo collision形状の確認が必要。
3. **Stamped/Unstamped二重入力（中、直接原因ではない）**: 同じ指令で`motion_control`の受信時刻が二重更新される。不必要な経路であり、今後の単一化候補。
4. **システム時刻とシミュレーション時刻の混在（低、直接原因ではない）**: header整合性と遅延解析を難しくするが、今回の反転時系列とは一致しない。
5. **Navigation入力タイムアウト（棄却）**: 上流に負速度はなく、タイムアウト動作は停止値のみ。

## 修正候補（未実施）

1. Create3初期姿勢とドックのcollision間隔を確認し、重なりまたは旋回時接触があれば、試験専用ワールド側で初期姿勢かドック位置を離す。
2. `/cmd_vel_unstamped -> unstamped_cmd_relay -> /cmd_vel -> motion_control`に統一するか、`motion_control`へのUnstamped直接経路に統一し、片方だけを使う。通常Create3経路への影響を評価してから変更する。
3. リレーと診断ノードに`use_sim_time=true`を設定し、全headerと受信時刻を同じROS時刻領域へそろえる。
4. 修正前後で本JSONLを再採取し、BUMP件数、`motion_control`負速度、到達誤差を比較する。

この調査では安全反射、制御計算、速度上限、ホモグラフィを変更していない。

## 自由空間配置との比較

試験専用起動だけを次の配置へ変更し、同じ目標`odom (0.0, 0.25)`、同じゲイン、同じ速度上限で再計測した。

- Create3世界座標: `(0.0, -0.75, yaw=0)`
- ドック: 試験専用起動では生成しない
- 通常起動: 従来どおりCreate3 `(0,0)`、ドックあり

通常配置ではドック原点がCreate3から0.157 m前方、ドックcollision中心はyaw反転後の世界座標`x=0.202 m`、最接近面は`x=0.182 m`である。Create3本体collision半径は0.164 mで本体基準の隙間は18 mm、バンパーメッシュ最大半径は約0.17768 mで、バンパーとドックcollisionの計算上の最小隙間は約4.32 mmしかない。これはドッキング姿勢として意図された近接配置だが、その場旋回時には接触し得る。

自由空間配置の静的collisionクリアランス概算:

| 対象 | Create3バンパーからの最短隙間 |
|---|---:|
| 左右壁 | 約2.72 m |
| 奥壁 | 約2.47 m |
| 植木鉢 | 約2.81 m |
| サイドテーブル | 約2.46 m |
| ドック | 生成なし |

比較結果:

| 指標 | 通常ドック近接配置 | 自由空間配置 |
|---|---:|---:|
| 非空hazardメッセージ | 43 | 0 |
| `bump_right` | 43メッセージ内で検出 | 0 |
| `motion_control`後退開始 | 8回 | 0回 |
| odom速度反転 | 8回 | 0回 |
| 最終位置誤差 | 0.274239 m | 0.1500000957 m |
| 到達判定 | false | false |
| 停止理由 | 到達タイムアウト | 到達タイムアウト |

自由空間では前後振動が解消し、Create3は初期odom `(0,0)`から`(0.006270, 0.100131)`まで前進した。残差は到達半径0.15 mの外側約`9.57e-8 m`（0.096 µm）である。現在の比例式は`linear_gain * (distance - arrival_distance)`なので、この時点の理論指令は約`3.83e-8 m/s`となり、Gazeboの実用的な移動分解能以下で漸近停止する。従って自由空間試験で残った未到達は接触やhazardではなく、到達境界へゼロ速度で漸近する終端条件による。

修正は実施していない。次工程の候補は、到達判定へ数値許容差を設ける、終端最小速度を設ける、または到達半径の内側に停止目標を置くことである。いずれもNavigation仕様変更になるため、別工程で選択・検証する。

## arrival_epsilon適用後

シミュレーション専用設定へ`arrival_epsilon=0.001 m`を追加し、共通コードと通常設定の既定値は`0.0`とした。同じ自由空間配置・同じ目標で再試験した結果:

| 指標 | 結果 |
|---|---:|
| 到達判定 | true |
| 到達時間 | 67.198 s |
| 最終位置 | `(0.006210, 0.099150, 1.534627)` |
| 目標までの停止距離 | 0.150977 m |
| 許容差込み閾値 | 0.151000 m |
| 閾値内側の余裕 | 0.0000226 m |
| 初期位置からの移動距離 | 0.099345 m |
| 到達後の非ゼロ指令 | 0件 |
| 非空hazard | 0件 |
| 指令・実速度反転 | 0件 |
| 目標喪失停止 | 成功 |
| 入力タイムアウト停止 | 成功 |
| 終了後制御無効化 | 成功 |

停止理由は`target reached; target-loss timeout stop verified`。到達状態は同一目標に対してラッチされ、到達後は毎周期ゼロ速度を明示送信する。新しい目標または目標消去でラッチを解除する。
