## 1. タスクの目的：何を実現するか

本課題では、**固定カメラのAI物体認識に基づき、床面の対象物を移動目標として扱い、Roomba 680を制御するPhysical AIシステム**を構築した。

目標とするタスクは、次の一連の動作である。

1. カメラ画像から床面のごみ候補を検出する。
2. Roombaの位置・向きと対象の位置を床面座標で把握する。
3. 対象へ向かう旋回・前進の行動候補をROS 2で計算する。
4. 明示的に許可された行動をPico W経由でRoombaの左右車輪へ送る。
5. 対象の消失、姿勢の喪失、通信異常、または試行終了時には停止する。

**課題としての実証範囲**は、認識結果から実機へ低速の走行指令が届き、有人の限定試験で物理的な移動と停止が成立するところまでである。実機がごみへ連続接近して到達する閉ループ全体、実物の吸引・収集、無人運転は未達である。

## 2. AIを使用する場所と、通常の制御との境界

| 機能 | 技術 | AIか | 本課題での役割 |
|---|---|---|---|
| 対象物の検出 | **YOLO** | **学習済みAIの推論** | USBカメラ画像からマスク等の対象、bbox、confidenceを抽出 |
| ロボット姿勢の把握 | OpenCV **ArUco** | 幾何計算 | マーカーID 0からRoomba位置・向きを推定 |
| 移動候補の計算 | **ROS 2 Navigation**制御ノード | 従来型の制御 | 対象と現在姿勢の差からTwist（前進・旋回）を計算 |
| ROS 2から実機への出力 | output adapter・TCP bridge | 通信・制御 | 速度指令、ARM認可、ACK/STOPの管理 |
| 車輪への指令 | **Pico W＋Roomba OI** | マイコン・実機制御 | 左右速度のUART送信、走行期限・停止監視 |

**AIが直接車輪速度を生成するVLAではない。** 学習済みモデルは画像認識を担当し、その認識結果を古典的な座標変換・Navigation・実機制御へ接続した点がPhysical AIとしての実装上の中心である。

## 3. ロボットが実際に達成した行動

### 提出時点で裏付けられる実機結果（2026-10-28〜29）

**10月28日：AI連動有人床面単発試験 — 限定PASS**

- カメラ認識→ArUco姿勢→ROS 2 Navigation→ARM→Pico W→Roomba OIの指令経路が実機でつながった。
- Roombaへ左右 **20／20 mm/s** の低速前進を指令。
- PicoでDrive sequence **1〜7**を記録し、最初のDriveから通常STOPまで**289 ms**。
- 人間が短い前進、両輪停止、異音なし、STOP後の再発進なしを確認。

これは**AI認識から実機の物理動作までの結合を確認した成果**である。ただし、目標までの自律到達を達成したわけではない。

**10月29日：期限停止の追加有人両輪浮上試験 — 別目的のPASS**

- ACK待ち中でもSTOPを優先する修正経路を検証。
- Picoの最初のDriveからSTOPまで**224 ms**。STOP後Drive **0件**、物理停止、再発進なし。
- 10月28日の「AI連動床面試験」とは別の試行であり、映像・説明で混同しない。

### 提出後の追加結果（2026-10-30、ローカル報告）

C3有人床面試験で、**同一ARM generationのまま1秒超のDrive、実測56 mm直進**を報告した（暫定距離許容40〜80 mm）。一方、Wi-Fi/TCPの遅延で次の指令がwatchdog STOP後に到着し、**規定時間の連続通信はFAIL**だった。

ACK再同期では停止後の実行済みsequenceを照合できたが、「通信障害中にも走行継続できた」とは判定していない。

**C3は追加成果であり、2026-10-29基準のGitHub提出コミットに含まれる実機証拠と区別する。** ソース・報告書・ログのリモート反映が確認できた段階で提出物への採否を検討する。

動画では、説明の主軸を次の順番に置く。

**AIが認識する → ロボットの姿勢・目標を求める → 移動指令を計算する → 実機が短時間前進する → 停止する。**

- **冒頭**：タスクを一文で提示し、固定カメラ、Roomba、システムの全景を示す。
- **認識**：YOLOの対象検出とArUcoの姿勢検出を画面で示す。
- **判断**：ROS 2のNavigation候補・矢印や目標位置を簡潔に可視化する。
- **実行**：実機で撮影できた範囲の前進映像、または証拠ログを正しいラベルで示す。
- **締め**：達成した「認識から実機駆動」と、未達の「自律到達・収集」を区別して示す。

Create 3／Gazebo映像は**simulation**、実Webカメラのdry-runは**real camera / non-driving**、有人Roomba走行は**attended hardware**と明記する。物理走行映像がない区間をシミュレーター映像で代用して「実機成功」に見せない。

提出動画の既存台本は[video_storyboard.md](video_storyboard.md)。この方針は**構成の整理案**であり、提出済み動画がこの順に編集されていると確認したものではない。公式の動画時間・形式は別途要項を確認する。

## 6. 工夫した点

1. **認識・姿勢・制御を別モジュール化**：YOLO、ArUco、ROS 2をつなぎ、simulationと実機出力先を切り替えられるようにした。
2. **実機で生じた通信障害の原因解析**：MicroPythonのnon-blocking `socket.send()`の`None`の扱いがARM ACK消失を引き起こした問題を修正し、ACK全バイト送信後のARM確定へ変更した。
3. **STOPと走行認可の分離**：世代番号、sequence、期限、watchdog、STOPラッチで意図しない再送・再発進を抑える設計を採用した。
4. **証拠を実機と模擬で分離**：実画像の非走行、Create 3 simulation、有人床面、両輪浮上を混同せず、各々の実測と未確認を残した。
5. **オドメトリを段階的に開発**：ROS 2のreplay/dry-run経路は完成させ、実機encoder取得とNavigation融合は未統合と明記した。

## 7. 400 ms期限超過の位置づけと今後の課題

ホスト400 ms期限は、**課題タスクの「対象認識→実機動作」とは別に設定した追加の停止性能評価項目**である。

旧20 Hz監視の試行では、ホスト側STOP開始に約**41.8 ms**の超過が観測された。100 Hz化だけでは、同期Safe照会やACK待ちがROS executorを塞ぐ問題が残ったため、TCP応答待ちの途中でも期限を監視してSTOPへ移る方式に改修した。

後続の有人両輪浮上試験ではPico相対のDrive→STOP **224 ms**、STOP後Drive 0件を確認。一方、その試行の**厳密なホストSTOP開始時刻は保存されておらず、「400 ms以内を実機保証」とは書かない**。STOP ACK `0x07`、要求車輪速度左右0、OI Safe mode 2などの状態確認と、物理停止の目視確認も区別する。

今後の主要課題は、実機での左右旋回・目標到達、通信連続性、Roomba実encoder 43/44のROS 2統合、カメラ姿勢推定との実測比較、ブリッジ孤児化を防ぐ実験操作の簡素化である。

## 結論

本課題では、**YOLOによる対象認識をROS 2の移動判断につなげ、Pico W経由でRoomba 680の限定的な低速床面動作を実現した。** AIの推論範囲と従来制御の範囲を切り分け、実機・非走行・シミュレーションの証拠を区別して評価した。通信・停止の追加性能試験には未達項目があるが、それをタスクの認識→実機動作の限定達成と混同しない。閉ループ自律到達と実機オドメトリは今後の課題とする。
